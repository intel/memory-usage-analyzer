# Redis Server/Client VM Memory Benchmark

Runs **Redis servers driven by memtier_benchmark across paired KVM virtual
machines** to obtain an initial **memory estimation** for the Redis workload and
to measure the impact of the zswap/zram compressor (IAA vs. lz4/zstd) on
throughput/latency under memory pressure.

This is the VM counterpart of [`tests/redis`](../redis/readme.md). It reuses the
script architecture of [`tests/kernelbuild_vm`](../kernelbuild_vm/README.md) but
swaps the guest workload for Redis + memtier, and splits the load generator into
its own VMs.

## Topology

- **`V` server VMs**, each running **`N` redis instances**. Each instance is
  sized for the dataset (`--mem-per-instance`, default 6 GB), so a server VM gets
  `N × mem_per_instance` GB of RAM.
- **`V` client VMs** running `memtier_benchmark`, **paired 1:1** with the servers:
  `client<i>` drives every redis instance of `server<i>`.
- **Only the SERVER VMs are placed in the host cgroup** (`memory.max` swept
  down). Their anonymous guest memory is what the host kernel compresses. **Client
  VMs run unconstrained**, so the load generator is never the bottleneck — we are
  benchmarking the *servers*.

```
┌───────────────────────────────────────────────────────────────────────┐
│ Host                                                                    │
│                                                                         │
│  cgroup redisbench_vm  (memory.max swept down)   ── UNCONSTRAINED ──     │
│  ┌───────────────────────┐                       ┌───────────────────┐  │
│  │ server1  (N×6GB)       │  ◀── memtier ───────  │ client1 (2GB)     │  │
│  │  redis :9001..900N     │   10.0.2.2:16000..    │  N memtier procs  │  │
│  ├───────────────────────┤                       ├───────────────────┤  │
│  │ server2  (N×6GB)       │  ◀── memtier ───────  │ client2 (2GB)     │  │
│  │  ...                   │                       │  ...              │  │
│  └───────────────────────┘                       └───────────────────┘  │
│        All SERVER RAM is ANONYMOUS → host compresses it under pressure   │
│        → zswap (IAA / lz4 / zstd) → server throughput/p99 impact         │
└───────────────────────────────────────────────────────────────────────┘
```

### Why run Redis inside a VM?

A native Redis run has a **page-cache escape hatch**: under memory pressure the
host kernel drops file-backed pages before compressing anonymous memory, so
compressor speed barely shows. With a VM, **all guest memory is anonymous to the
host kernel** — there is no page-cache escape, so tightening the server cgroup's
`memory.max` forces the redis dataset through compressed swap on every fault and
compressor speed directly impacts throughput and p99.

### Networking

QEMU user-mode (SLIRP) — **no bridges or `NET_ADMIN` required**. Each server VM
forwards its redis instance ports `9001..900N` to unique host ports
(`16000 + (server-1)·N + (instance-1)`). The paired client VM reaches them via
the SLIRP gateway `10.0.2.2:<host_port>`. SSH ports: servers `2240+`, clients
`2340+`.

### CPU planning

Server and client VMs get **disjoint host-core blocks**, pinned with `numactl`:

- `--core-policy contiguous` (default): servers occupy the first cores, clients
  the block after them.
- `--core-policy numa-split`: servers on NUMA node 0, clients on node 1 (when
  both fit), physically separating load generation from the servers.
- `--server-cpusets "0-3;4-7"` / `--client-cpusets "8-10;11-13"`: explicit
  per-VM override (semicolon-separated, one entry per VM).

## Defaults

- **1 server VM + 1 client VM**, **1 redis instance**, **6 GB/instance**
- Server vCPUs = `instances + 1`; client vCPUs = `instances`
- Dataset: `import_movies_10000r_10c.redis`, generated locally by the bundled
  [`repeat_redis_file.py`](repeat_redis_file.py) (`-r 10000 -c 10`) and staged
  into the client VM images by `benchmark.sh` on first run. The client loads it
  into the paired server once (`.redis` via `redis-cli --pipe`, `.csv` via
  `memtier_benchmark --data-import`). If the dataset is missing, `benchmark.sh`
  exits with guidance.

## Prerequisites

- Linux host with KVM support (`/dev/kvm`)
- QEMU (`qemu-system-x86_64`, `qemu-img`, `qemu-nbd`)
- `genisoimage` or `cloud-localds` (for cloud-init ISO)
- SSH client, `numactl`
- zswap or zram configured with a swap backend
- IAA hardware + drivers (for the IAA compressor profiles)
- A host-built `memtier_benchmark` on `PATH` (run
  [`../redis/setup_redis.sh`](../redis/setup_redis.sh) once) — staged into the
  client VMs because the guests have no outbound network
- The Redis dataset `import_movies_10000r_10c.redis`, generated by the bundled
  [`repeat_redis_file.py`](repeat_redis_file.py) (needs `pandas`, `numpy`,
  `matplotlib`, `requests`); the base input `import_movies.redis` is downloaded
  automatically by the generator on first run

## Quick Start

The workload runs in **three steps** — set up the VM images once, generate the
dataset, then run the benchmark:

```bash
# 1. One-time VM setup (Ubuntu cloud image, kernel/initrd, memtier binary, SSH
#    keys). Does NOT generate or stage the dataset.
./setup_vm.sh

# 2. Generate the default dataset (import_movies_10000r_10c.redis)
python repeat_redis_file.py -r 10000 -c 10

# 3. Run the benchmark — stages the dataset into the VMs, boots them, and runs
#    the baseline memory estimation + compression sweep
./benchmark.sh
```

### Default run

With no flags the benchmark uses the defaults — **1 server VM + 1 client VM, 1
redis instance at 6 GB**, all built-in compressors, zswap:

```bash
./setup_vm.sh                              # 1. one-time image setup
python repeat_redis_file.py -r 10000 -c 10 # 2. generate the dataset
./benchmark.sh                             # 3. run (1 server × 1 instance × 6 GB)
```

Scale up by passing the topology flags to `benchmark.sh`, e.g. 2 server VMs each
running 3 instances at 6 GB (2 paired client VMs):

```bash
./benchmark.sh --server-vms 2 --instances 3 --mem-per-instance 6
```

`setup_vm.sh` only needs to run **once**: it produces the count-independent
artifacts (base image, kernel/initrd, memtier binary, SSH key). `benchmark.sh`
regenerates the per-VM overlays and cloud-init for whatever topology you pass it,
so you can change `--server-vms` / `--instances` at benchmark time **without
re-running setup**. Set `PYTHON=/path/to/python` to pick the interpreter that has
the generator's dependencies.

## Sizing and host limits

Before booting, `benchmark.sh` checks that the VMs fit the host:

- **Server VM RAM** = `instances × mem_per_instance` GB.
- **Total VM RAM** = `server_vms × server_RAM + client_vms × client_mem`
  (client VMs default to 2 GB each).
- The run **aborts** if total VM RAM exceeds `host RAM − 10%` (min 8 GB reserved).

Example: `--server-vms 10 --instances 10` at the default 6 GB/instance needs
`10 × (10 × 6) = 600 GB` for servers plus `10 × 2 = 20 GB` for clients = **620 GB**,
requiring roughly **≥ 690 GB** host RAM. Lower `--mem-per-instance`,
`--instances`, or `--server-vms` if you hit the "exceeds available host RAM" error.

**CPU pinning:** server VMs get `instances + 1` vCPUs, client VMs get `instances`
(min 1). With the default `contiguous` policy the VMs want
`server_vms × (instances+1) + client_vms × instances` disjoint host cores for
clean pinning; with fewer cores the later VMs run unpinned (they still run, but
contend for cores). Use `--core-policy numa-split` or explicit
`--server-cpusets` / `--client-cpusets` to control placement.

## Scripts

| Script | Purpose |
|--------|---------|
| `setup_vm.sh` | One-time setup: download cloud image, extract kernel/initrd, stage the memtier binary, generate SSH keys + base overlays/cloud-init. Does **not** touch the dataset — generate it separately; `benchmark.sh` stages it |
| `benchmark.sh` | Main orchestrator: boot servers (in cgroup) + clients (unconstrained), start empty server instances, prefill them from the clients, baseline run, sweep server memory limits, collect results |
| `vm_lib.sh` | Role-aware VM lifecycle library (start/stop, networking, CPU plan, cloud-init, workload deployment, pre-flight) |
| `vm_ctl.sh` | Utility: start/stop/status/ssh into server or client VMs |
| `report.py` | Parser + text reporter for the benchmark log lines |
| `repeat_redis_file.py` | Dataset generator (bundled from `tests/redis`) |

The HTML plot reuses the native Redis plotter
[`../redis/report_plot.py`](../redis/report_plot.py).

## How It Works

1. **Setup** (`setup_vm.sh`): Creates one Ubuntu cloud-init base image (installs
   `redis-server`, `redis-tools`, and the memtier runtime libraries) and stages
   the host-built `memtier_benchmark` binary. The dataset is **not** handled here
   — generate it separately (step 2) and `benchmark.sh` stages it into the images
   directory on first run. `benchmark.sh` (re)creates the per-VM overlays and
   cloud-init ISOs for `V` server and `V` client VMs for whatever topology you
   pass it.

2. **Benchmark** (`benchmark.sh`):
   - Computes the disjoint server/client CPU plan
   - Configures the host zswap/zram compressor (IAA, lz4, zstd, ...)
   - Boots **server VMs inside the cgroup** and **client VMs outside it**
     (unlimited during boot)
   - Stages the dataset **and** memtier into the client VMs once, then
     snapshots the overlays so every scenario restores a clean disk quickly
   - Runs a **baseline** scenario (unlimited) → peak *server* memory estimation
     and baseline aggregate throughput
   - Sweeps the **server** memory limit down (% of baseline peak), aborting once
     aggregate throughput regresses beyond the threshold
   - Emits log lines compatible with `report.py` / `../redis/report_plot.py`

3. **Guest workload** (`run_workload.sh`, deployed over SSH):
   - `server-start` (server VMs): start `N` empty redis instances on ports
     `9001..900N`, each pinned to a guest core
   - `client-prefill` (client VMs): populate the paired remote server
     (`10.0.2.2:<host_port>`) from the dataset — `redis-cli --pipe` for `.redis`
     files, or `memtier_benchmark --data-import` for `.csv` files
   - `client-run` (client VMs): launch one `memtier_benchmark` per remote
     instance (`10.0.2.2:<host_port>`, Gaussian 20:80 write:read), then aggregate
     `throughput` (sum), `p99` (max) and `instances` into `benchmark_result.txt`

Each scenario re-boots the VMs, starts the server instances, applies the server
memory limit, prefills them from the clients, and then runs memtier from the
clients under pressure.

## Options

### setup_vm.sh

```
--server-vms <V>        Number of server VMs (client VMs match 1:1) (default: 1)
--instances <N>         Redis instances per server VM (default: 1)
--mem-per-instance <GB> RAM per redis instance; server VM RAM = N*this (default: 6)
--client-mem <GB>       RAM per client VM (default: 2)
--vm-disk <GB>          Overlay disk size in GB (default: 20)
--db-file <name>        Redis dataset file (default: import_movies_10000r_10c.redis)
```

`setup_vm.sh` does **not** generate or stage the dataset. Generate it separately
with the bundled generator (`python repeat_redis_file.py -r 10000 -c 10`);
`benchmark.sh` stages the resulting file into the VM images on first run. Use
`--db-file` if you generated a differently named dataset.

### benchmark.sh

```
--server-vms <V>          Number of server VMs (client VMs match 1:1) (default: 1)
--instances <N>           Redis instances per server VM (default: 1)
--mem-per-instance <GB>   RAM per redis instance; server RAM = N*this (default: 6)
--client-mem <GB>         RAM per client VM (default: 2)
--server-vcpus <N>        vCPUs per server VM (default: instances + 1)
--client-vcpus <N>        vCPUs per client VM (default: instances)
--core-policy <p>         contiguous | numa-split (default: contiguous)
--server-cpusets <map>    Explicit per-server host cpusets, ';'-separated (e.g. "0-2;3-5")
--client-cpusets <map>    Explicit per-client host cpusets
--db-file <name>          Redis dataset file (default: import_movies_10000r_10c.redis)
--data-reps <N>           Resolve repeat_redis_file.py dataset name (-r); match setup_vm.sh
--data-cols <N>           Combined lines used for generation (repeat_redis_file.py -c)
--data-input <file>       Base input used for generation (default: import_movies.redis)
--duration <sec>          memtier run duration per scenario (default: 120)
--swap-mode <mode>        zswap or zram (default: zswap)
--compressor <name>       Compressor profile or 'all' (default: all)
  --sweep-start <pct>       Sweep start, % of baseline peak (default: 80)
  --sweep-end <pct>         Sweep end,   % of baseline peak (default: 40)
--sweep-step <pct>        Sweep step in % (default: 2)
--threshold, -t <pct>     Throughput regression threshold to stop sweep (default: 10)
--logdir, -l <path>       Output directory (default: ./logdir)
```

Compressor profiles follow the `<algo>_r<reclaim-batchsize>_p<page-cluster>`
convention, e.g. `deflate-iaa_r64_p5`, `zstd_r1_p3`, `lz4_r1_p3`.

### vm_ctl.sh

```
vm_ctl.sh start [target]         Start VM(s)          (default: all)
vm_ctl.sh stop  [target]         Stop VM(s)           (default: all)
vm_ctl.sh status                 Show VM status
vm_ctl.sh ssh   <role> <id>      SSH into a VM        (e.g. ssh server 1)
vm_ctl.sh run   <role> <id> <cmd...>   Run a command in a VM

  target: all | servers | clients | server<i> | client<i>
```

## Output

Results are written to `logdir/` in the same format as the native Redis
benchmark:

- Per-scenario `<scenario>.log` files (e.g. `baseline.log`, `memlimit-90.log`)
  with throughput, p99, and compression stats
- Per-scenario sub-directories (e.g. `baseline/`, `memlimit-90/`) holding the
  `zswap_run.csv` sample log plus per-VM `server<i>/` and `client<i>/` workload
  output
- One `<compressor>.report` tabular summary per compressor (from `report.py`)
- Bokeh HTML plot from `../redis/report_plot.py`, named
  `<compressor>_thr<threshold>_report.html` for a single compressor or
  `combined_<N>_thr<threshold>_report.html` across `N` compressors. The plot
  only draws points where every redis instance produced a valid result
  (`actual_instances == configured_instances`); incomplete scenarios are still
  listed in the `.report` tables but omitted from the tradeoff curve.

The **baseline** `memory_peak` (from the server cgroup) is the initial memory
estimation for the Redis workload; compare it against the native
[`../redis/logdir`](../redis) results.

## Notes

- `setup_vm.sh` runs once to build the count-independent images; `benchmark.sh`
  regenerates the per-VM overlays/cloud-init, so its `--server-vms` /
  `--instances` can differ from setup without re-running it. Keep
  `--mem-per-instance` / `--client-mem` within your host's RAM budget (see
  [Sizing and host limits](#sizing-and-host-limits)).
- Only server VMs are memory-limited; client VMs run unconstrained.
- `configured_instances` = `V × N` total redis instances; `actual_instances` =
  instances that produced a valid result. `throughput_agg` is the summed ops/sec
  across all instances, `throughput` the per-instance mean, `p99` the max.
- Each redis instance needs `mem_per_instance` GB large enough to hold one full
  dataset copy *plus* redis RSS overhead and the guest OS. The default 6 GB fits
  the ~2.6 GB `import_movies_10000r_10c.redis` dataset; a smaller value (e.g. 3 GB)
  OOM-kills redis during prefill. Lower the generation `-r` to shrink the dataset
  or raise `--mem-per-instance` for more sweep headroom.
- The cgroup used is `/sys/fs/cgroup/redisbench_vm`.
